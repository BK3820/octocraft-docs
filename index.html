Platform documentation

OctoCraft Platform Documentation

GitHub, managed as code: how OctoCraft turns a reviewed request into a GitHub App, where its credentials go, and how the platform is built, secured, tested and deployed.

Proof of concept As of 17 Nov 2026 Go · Helm · Terraform · AKS Apache-2.0

01Overview

OctoCraft turns a structured request into a GitHub App and delivers its credentials to a vault, with a person approving each app before it exists. It is a working proof of concept: the AKS runtime is deployed for internal use, and the original Azure Functions runtime is torn down.

How it works in one line: request → reviewed manifest → browser-confirmed GitHub App → credentials in Key Vault, HashiCorp Vault or a ZIP outbox.

  • Intake. Requests arrive from a GitHub issue form (IssueOps) or, in the standalone runtime only, from ServiceNow catalog tasks (SCTASK, “Phase 0”).
  • Review. Approvers see the requested permissions, owner and delivery target in the OctoCraft dashboard.
  • Creation. GitHub requires a signed-in person to confirm the app; OctoCraft never creates an app on its own.
  • Handoff. OctoCraft exchanges GitHub’s one-time code for the app’s ID, private key and secrets, then writes them to the chosen destination.

The backend is Go; the dashboard is a single static HTML/CSS/JavaScript page. The code is licensed under Apache-2.0.

02Architecture

OctoCraft is one Go server behind an identity proxy. It talks to four outside systems: the IssueOps workflow, ServiceNow, GitHub and Azure Key Vault.

GitHub’s redirect to /callback returns through the approver’s browser and the proxy. In the dormant Functions runtime, Easy Auth replaces the proxy, and Azure Table Storage plus a Blob outbox replace the PVC.

04Capabilities

OctoCraft automates one operation end to end today: GitHub App creation. ServiceNow intake also routes three more operation types, but OctoCraft refuses to approve or run them until each is registered.

GitHub App requests (IssueOps)

  1. A requester submits the GitHub App request issue form.
  2. The IssueOps workflow parses the issue into a manifest and posts it to POST /api/ingest with a bearer token. It then comments a review link and adds the awaiting-approval label.
  3. An approver reviews permissions, owner and delivery target in the dashboard, then selects Create on GitHub.
  4. The browser posts the manifest to GitHub, and a person with app-creation rights confirms it.
  5. GitHub redirects to /callback. OctoCraft exchanges the one-time code for the app ID, client secret, private key and webhook secret.
  6. Credentials go to the chosen destination. Only then is the request marked created.
StatusMeaningNext actions
pendingIntake complete; no app yetStart, simulate (if enabled), reject
awaiting_githubBrowser flow started; the user may have abandoned GitHubStart again, reset, reject
failedGitHub code conversion returned an errorInspect, reset, start again
createdCredentials deliveredView metadata, download outbox file
rejectedOperator rejected it; reason recordedSame app name may be requested again

ServiceNow intake (Phase 0)

The standalone server polls ServiceNow catalog tasks (sc_task) through Azure API Management every 300 seconds. Each ticket becomes one job. Routing uses only the catalog item ID and structured request variables; free text never selects an operation. Exactly one rule must match, otherwise the job is marked needs_mapping or ambiguous.

Routing ruleOperationApproval policySupported today?
github-app-creategithub_app.createstandard-adminManual handoff to the GitHub App flow
repository-createrepository.createstandard-adminNo: operation not registered
shared-github-catalog-grantrepository.team_access.grantaccess-changeNo: operation not registered
shared-github-catalog-removerepository.team_access.removeaccess-changeNo: operation not registered
  • Approvals: both policies need one approver, block requesters from approving their own job, and bind the approval to a hash of the normalized plan. Approval is refused when the operation is unregistered or the ServiceNow requester cannot be resolved.
  • No auto-execution: processing.auto_execute is false; an approved github_app.create job becomes manual_action_required.
  • Writeback: status updates to ServiceNow go through a separate leased outbox. The sample connection has update_task: false, so writeback shows as a manual action.
  • Sample data: the snow-prod connection is disabled, its base URL is api.example.com, and the catalog IDs are placeholders.

06Security and access

OctoCraft does not sign users in itself: an identity-aware front door does, and OctoCraft trusts the identity it forwards. On Functions that is Easy Auth with Entra ID; on AKS it is an Entra OIDC proxy (oauth2-proxy).

Identity and roles

  • Trusted headers. /api/v1 reads X-Octocraft-Subject and X-Octocraft-Roles only from OCTOCRAFT_TRUSTED_PROXY_CIDRS. Outside development mode, the server refuses to start without at least one CIDR of /16 or narrower. The proxy must strip client-supplied copies.
  • Development sign-in. OCTOCRAFT_DEV_AUTH=true grants roles to loopback clients only. Helm never enables it.
  • IssueOps ingest. POST /api/ingest checks a bearer token with a constant-time comparison.
  • GitHub App workspace. These routes have no in-app role check; access depends entirely on the front door. Actions are attributed from X-MS-CLIENT-PRINCIPAL-NAME.

Roles match exactly. admin does not inherit the other roles, so a person who needs to approve and run jobs needs approver and operator as well.

Phase 0 actionEndpointRequired role
Read connections, sync runs, tickets, jobs, eventsGET /api/v1/...Any of the five roles
Test a ServiceNow connectionPOST /api/v1/connections/{id}/testadmin
Trigger a sync, reprocess a ticketPOST .../sync, POST .../reprocessoperator
Approve or reject a jobPOST /api/v1/jobs/{id}/approve, .../rejectapprover
Execute a jobPOST /api/v1/jobs/{id}/executeoperator

Workload hardening (Helm)

  • Runs as non-root UID 10001 with a read-only root filesystem, all Linux capabilities dropped and a seccomp profile.
  • Service account token is not mounted; the Service is ClusterIP with no public ingress.
  • A NetworkPolicy admits port 3000 only from pods labelled oauth2-proxy in the octocraft-auth namespace.
  • Tokens are mounted read-only from the octocraft-secrets Secret; Helm values never hold credentials.
  • Workload Identity grants the pod Key Vault Secrets Officer on its own vault only.

Repository governance

  • CODEOWNERS assigns every path to BK3820.
  • The main ruleset requires a pull request with one code-owner approval, linear history and green build, terraform and ui checks. It blocks deletion and force-push. It is stored in Git and applied after the GitHub plan upgrade.
  • The production environment accepts only main and has admin bypass disabled. GitHub rejected required-reviewer enforcement on the current plan, so the Functions deploy uses a manual-approval issue instead.

Sensitive data to handle with care

  • ZIP outbox files contain live credentials; email drafts are neither sent nor encrypted.
  • Terraform state for the Functions runtime contains the ingest token.
  • Entra sign-in admits the whole tenant; it is not an approver allowlist.

07Running locally

The fastest path is go run ./cmd/server with development sign-in, which serves the dashboard at http://localhost:3000 in a few seconds. It uses a local file store, a mock vault and a local ZIP outbox, so it never touches GitHub or Azure.

OCTOCRAFT_SQLITE_PATH=./data/octocraft.db OCTOCRAFT_DEV_AUTH=true go run ./cmd/server

The server binds to all interfaces, so do not run development mode on a shared network. Local data under data/ is ignored by Git.

Add sample requests

npm ci
npm run seed

The seed posts three requests through the real IssueOps parser: acme-ci-bot (Vault), release-notifier (ZIP) and security-scanner (Vault). Use Simulate in the dashboard to exercise credential delivery with fake values.

Run in a container

docker compose up --build --detach
docker compose logs -f app
docker compose down            # --volumes also deletes local data

Compose publishes only on 127.0.0.1:3000, runs as UID 10001 with a read-only root filesystem, drops all capabilities and keeps data in the factory-data volume.

Run the Azure Functions worker

cp local.settings.example.json local.settings.json
func start

What a release run does

An operator starts Deploy AKS release (manual) from main. Runs are serialized, limited to 60 minutes, and use the aks-poc environment.

  1. Resolve the latest stable GitHub Release once and confirm its OCI chart exists. A failure here stops the run before any Azure change.
  2. Sign in to Azure through GitHub OIDC as id-octocraft-aks-deployer; no client secret exists.
  3. Create or verify the remote state storage.
  4. Initialise Terraform, import any existing resource missing from state, validate and plan.
  5. Stop if the plan deletes or replaces anything; otherwise apply the saved plan.
  6. Run helm upgrade with the exact chart and image version.
  7. Wait for rollout, check /api/health through a loopback port-forward, and write a run summary.

The deployer identity holds Contributor on rg-octocraft-aks, Cluster User on the cluster, Managed Identity Operator on the control-plane identity, and RBAC Administrator only on the outbound IP and Key Vault. On the state group it holds Contributor and Storage Blob Data Contributor.

Rollback, backup and recovery

  • Rollback: a reviewed helm upgrade to the previous release tag. A normal run always picks the latest release.
  • Blocked plan: fix drift in a separately reviewed change. Never remove the delete guard or delete the PVC or Key Vault to get a green run.
  • Backup: cmd/dbbackup takes an online SQLite backup and runs PRAGMA integrity_check. Store copies outside the PVC and test a restore before relying on them.

Azure Functions runtime (dormant)

scripts/provision.sh recreates the Functions infrastructure with Terraform, and deploy.yml deploys it behind an approval issue that waits up to 6 hours. The illustrative low-volume Azure cost is about $2.85/month. Both stay off while APP_FACTORY_ENABLED=false.

10Review findings

The setup is a well-documented, security-conscious proof of concept. Two gaps matter most before wider use: the GitHub App workspace has no role check of its own, and credentials can be lost after GitHub’s one-time exchange.

What is working well

  • Deployments are manual, run only from main, use OIDC with no stored cloud secrets, and stop on any destructive Terraform plan.
  • The workload is hardened: non-root, read-only filesystem, no capabilities, internal-only service, NetworkPolicy to the proxy.
  • ServiceNow approvals bind to a plan hash, block self-approval and never auto-execute.
  • Docs, diagrams and tests cover Go code, UI, Helm, Terraform and the deploy workflow.

11Roadmap

The platform design spec sets five phases. Only Phase 0 is built, and no phase has a date yet.

Phases 2 to 4 stay candidates until their API, backup, licensing and cost-data decisions are made.
